# Publishing to npm

The npm package is generated by Kotlin/JS. Publish from
`build/js/packages/dsl-kotlin`, not the repository root or `nodejs-test-project`.
The package name is `@zenwave360/dsl` and its version comes from
`build.gradle.kts`. Maven `1.9.0-SNAPSHOT` becomes npm `1.9.0-next.0` locally.
The shared workflow assigns `RUN_NUMBER.RUN_ATTEMPT`, producing a unique
version such as `1.9.0-next.123.1` on each run. All snapshots use the `next`
distribution tag. npm versions are immutable, so repeat publication cannot
overwrite `1.9.0-next.0`.

When the Maven version loses `-SNAPSHOT`, the npm version loses `-next.*`:
`1.9.0` becomes npm `1.9.0` and publishes under `latest`. `-PnpmVersion=VERSION` remains an
explicit override for manual package preparation.

## First publication

1. Create an npm account, enable two-factor authentication, and ensure it has
   publishing permission in the `zenwave360` npm organization.
2. Choose the npm version. The current development build defaults to
   `1.9.0-next.0`. To select another version without changing the Maven version,
   pass `-PnpmVersion=VERSION` to Gradle. Each published version must be unique.
3. Build and run the JavaScript tests. On Windows, from PowerShell:

   ```powershell
   .\gradlew.bat --no-daemon jsNodeTest jsProductionExecutableCompileSync nodeIntegrationTest
   ```

   On Linux/macOS, use `./gradlew` with the same arguments.
4. Inspect and pack the generated package:

   ```powershell
   Push-Location build/js/packages/dsl-kotlin
   npm pack --dry-run
   npm pack
   Pop-Location
   ```

   Verify that the package includes its `.mjs` runtime modules, TypeScript
   declarations, README, and LICENSE. Install the tarball in a separate test
   project and verify imports and parsing before publishing.
5. Log in interactively and publish the reviewed tarball (replace `VERSION`):

   ```powershell
   npm login --registry=https://registry.npmjs.org/
   npm whoami --registry=https://registry.npmjs.org/
   npm publish ./build/js/packages/dsl-kotlin/zenwave360-dsl-VERSION.tgz --access public --tag next --registry=https://registry.npmjs.org/
   npm view @zenwave360/dsl dist-tags --registry=https://registry.npmjs.org/
   ```

   Consumers opt in with `npm install @zenwave360/dsl@next`. Ordinary installs
   use `latest`; until a stable version has been published under `latest`, there
   is no default stable release to install. For an intended stable release, use
   a stable version and `--tag latest` instead. Keep passwords, tokens,
   and one-time codes in the interactive npm flow. A published name/version
   cannot be reused.

## Snapshot publishing through GitHub Actions

`.github/workflows/publish-maven-snapshots.yml` runs on pushes to `develop` and
`next`. It delegates npm publication to
`ZenWave360/release-workflows/.github/workflows/publish-snapshots-gradle.yml`
with `publish-npm: true` and the package name/directory. After the Maven snapshot
job succeeds, a separate shared job builds and tests
the JS package without Maven or signing credentials, then publishes its unique
version under `next` using npm OIDC trusted publishing.

After the manual first npm publication, add a GitHub Actions trusted publisher
in npm with organization `ZenWave360`, repository `dsl-kotlin`, workflow
`publish-maven-snapshots.yml`, and environment `npm-snapshots`. Create that GitHub
environment and restrict deployment branches to `develop` and `next`.
The first publication and trusted publisher configuration must be complete
before this job can publish successfully. No npm token is needed for publishing.

## Stable releases through GitHub Actions

The local `.github/workflows/release.yml` delegates to
`ZenWave360/release-workflows/.github/workflows/release-gradle.yml@main` and
provides `npm-package-dir: build/js/packages/dsl-kotlin`. Its `publishNpm`
dispatch input controls npm publishing alongside the Maven release.

After the first publication, configure npm trusted publishing in the package
settings. For GitHub Actions, use organization `ZenWave360`, repository
`dsl-kotlin`, workflow filename `release.yml`, and environment `npm-publish`
(the reusable workflow's default). Create that GitHub environment with a
required reviewer. Review the reusable workflow again before enabling it, since
the caller references its moving `main` branch.
Trusted publishing requires npm 11.5.1 or later and Node 22.14.0 or later on a
supported hosted runner.

The reusable workflow checks that the npm version matches the release version.
Dispatch version `1.9.0` and enable `publishNpm` to publish npm `1.9.0` under
`latest`. This drops the prerelease suffix automatically. For an intentional
prerelease through the release workflow, a version such as `1.9.0-rc.1` uses
`next` instead.

Dropping the suffix does not delete earlier prerelease versions or the registry's
`next` tag. Tag deletion is a separate authenticated operation:
`npm dist-tag rm @zenwave360/dsl next`. npm OIDC authentication supports publishing,
but not `dist-tag` operations. Do not unpublish snapshot versions to emulate
Maven snapshot replacement: npm will still refuse to reuse those versions.

The older instructions in `RELEASING.md` reference a missing
`docs/release-security.md`; consult the actual reusable workflow before relying
on its Maven approval or upload details.

References: [npm scoped public packages](https://docs.npmjs.com/creating-and-publishing-scoped-public-packages/),
[npm trusted publishing](https://docs.npmjs.com/trusted-publishers/).

CI npm versioning, tagging, building, and publication are centralized in
`release-workflows`; this repository contains package metadata and thin callers.
Commit and push the coordinated shared workflow changes before these callers
can use the new snapshot npm inputs.
